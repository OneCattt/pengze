# 彭泽三打一 · 原型验证稿

最终产品平台：微信小游戏。当前产物是基于 Figma 设计制作的本地 HTML 验证工具，供确认界面、流程与明确规则使用。

## 打开试玩

直接双击 `彭泽三打一_原型验证.html`，无需安装依赖、启动服务器或联网。字体、样式和脚本均已内嵌。

- 首页点击“开始游戏”：使用真实双副108张牌，与三个AI进行一局游戏。
- 点击牌桌左上角“彭泽三打一”或首页“验证场景”：进入独立验证场景。
- “展开手牌”：查看和选择完整25/33张手牌，适合小屏扣底。
- 当前操作20秒超时进入托管，持续自动出牌。验证稿不会擅自恢复手动；返回首页会开启新会话。
- 结算页的“结算明细”展开正常输赢与甩错额外转账，“累计”查看本会话的历史结算。
- “加速AI演示”仅缩短AI思考与动画，不改变真人20秒操作期限。
- 独立场景属于演示牌局，切换场景会替换当前牌局。正常游戏不包含提前结算按钮。

## 依据与优先级

- 规则依据：`彭泽三打一_完整规则与Figma原型需求_V1.md`，文件内容版本V1.1。
- 原型依据：[Figma · 彭泽三打一](https://www.figma.com/design/dROznof43d5cVxGKNj5vxM/Untitled?node-id=2-7486)。
- 已读取起始、叫分、定主、扣底、首攻、超时、规则、结算等节点的设计上下文，并按原型缩放关系还原844×390牌桌。
- 延续原型的绿色渐变、细金边、四方座位、中央徽记、底部牌扇、金色主按钮、深绿操作条及结算面板。
- 使用内嵌的Noto Serif SC、Noto Sans SC，不依赖临时Figma资产链接或在线字体。

## 传统扑克牌面升级

采用 [Public Domain and CC0 Playing Cards](https://github.com/AustinGabriel/Public-Domain-and-CC0-Playing-Cards) 的完整54种传统牌面：52张普通牌、黑色小王和红色大王。固定来源版本、CC0许可、原始SVG及图片指纹保存在 `assets/cards/`。

- 按原始5:7比例导出240×336 WebP，总计约521KB，相比原始SVG减少约91.5%。构建后的独立HTML约1.12MB。
- 手牌、展开手牌、出牌、扣底翻面及结算底牌使用同一套图片；原有绿色“彭”字牌背继续保留。
- 重叠手牌叠加清晰的点数、花色和大小王角标，选中时抬起并显示金边。展开区域支持完整查看33张牌。
- 两副牌复用54种图像，108张实体牌ID保持独立。图片仅参与展示，游戏规则实现没有变化。
- 图片全部内嵌，无需联网。当前仍属于本地HTML验证，微信小游戏的资源打包与真机表现待正式工程验证。

素材授权和重新导出方法见 [`assets/cards/README.md`](assets/cards/README.md)。

原型中的示意牌不直接用作牌局数据。例如S10选中大小王却标注“对子”，验证稿依据规则纠正：只有两张同花色、同点数的牌才是对子。所有实际手牌来自唯一的108张实体牌，不能复制示意牌凑数量。桌面底牌显示真实8张牌背，AI收底与扣底不泄露牌面。

## 已接入真实逻辑

- 真实洗牌、逐张发牌、每人25张和底牌8张。
- 看牌后叫分；80起叫、5分步长、跳叫、退出、不设上限，200分以上也可叫。
- 全员不叫按首叫位−30、其余各+10结算。
- 庄家25→33→定主→扣8→25→首攻；扣王、主牌、分牌均合法。
- 单张、对子、同长度拖拉机、王对与主A对相连、同级先出者保留牌权。
- 强制先跟花色、有对跟对、有同长度拖拉机跟拖拉机；缺门垫牌和对应结构主牌杀牌。
- 明确的单张/对子甩错：仅打出失败部分，庄家每张扣10分，闲家每张向庄家支付15元。
- 实际牌墩抓分、扣底不计分、不设抠底、负有效分、金额守恒、逐位结算。
- 20秒操作倒计时、持续托管、阶段切换清除旧计时。
- 下一局保留局数、座位、累计金额，并按文档暂定方式轮换首叫。

## 仍需具体牌例的范围

规则文档明确不允许凭“传统升级”自行编造地方差异算法。当前验证稿对下列情况在提交前返回明确提示，保持牌、罚分和金额不变：

1. 有部分连对但无同长度拖拉机时，复杂拆分跟牌的严格优先级。首攻时会预检，避免进入中途无法继续的牌墩。
2. 成功混合甩牌后的完整跟牌结构与多人杀牌比较。
3. 多类失败结构同时存在或拖拉机失败时，最小失败结构的具体选择。
4. 存在缺门并有主牌的对手时，杀牌是否影响甩牌检查的地方差异。

这些边界没有简化为“比最大一张”。正常AI首攻使用单张或对子，能够完整打完一局；250局AI验证不代表上述复杂组合已验收。

金额公式仍是文档的暂定V1；叫分/定主20秒、首叫轮换等继续保留文档状态。取消托管和跨局保持的最终口径、微信前后台恢复规则尚未确定，本稿不自行补充。

## 源码与重建

| 文件 | 用途 |
|---|---|
| `src/page.html` | 单文件页面模板 |
| `src/style.css` | 基于Figma的牌桌样式 |
| `src/rules.js` | 牌组、明确规则、记分、状态机与AI |
| `src/app.js` | 页面、计时、动画、交互及独立演示场景 |
| `assets/*.woff2` | 内嵌字体源文件 |
| `assets/cards/` | CC0原始牌面、优化图片、许可与来源清单 |
| `build.cjs` | 将源码和字体构建为可独立打开的HTML |
| `verification/check.cjs` | 无额外依赖的规则检查和AI完整牌局验证 |
| `verification/browser.cjs` | Playwright浏览器行为与截图验证 |
| `verification/visual.py` | Figma桌布颜色对照与并排图 |
| `verification/prepare-fonts.py` | 根据界面所需字符获取设计字体子集，内容变化需要新字形时使用 |
| `verification/prepare-cards.cjs` | 固定上游版本，获取SVG并用Sharp生成WebP，仅素材再生成时需要 |

已有字体源文件时，重建和规则验证只需Node.js：

```sh
node build.cjs
node verification/check.cjs
```

浏览器检查需要Playwright及Chromium；可通过`NODE_PATH`指定已有运行时依赖，通过`PENGZE_CHROMIUM`指定浏览器可执行文件，然后运行：

```sh
node verification/browser.cjs
python3 verification/visual.py
```

HTML内的`window.PengzeValidation`只用于本地验证，提供独立场景、冻结、状态检查和测试超时触发入口。`?review=bid`等链接会冻结操作计时，便于静态评审；正常打开文件则按真实流程计时。该验证接口不是微信小游戏的生产接口。
